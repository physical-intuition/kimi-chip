## X4 harness and frequency-escalation protocol

This protocol supersedes the old constant-400 MHz approach for X4. Leave X3 on its existing methodology through Y5. Do not pre-plan, specify, or implement X5 yet. X5 must emerge only after all X4 evidence exists.

Before X4-Y1, read every entry in `experiments/x1/trials.jsonl`, `experiments/x2/trials.jsonl`, and `experiments/x3/trials.jsonl`, including both successes and failures. Build a machine-readable failure-pattern summary tied to raw artifacts. Extract recurring functional, timing, electrical, congestion, routing, and methodology failures. Write X4's initial lint rules from those observed patterns, with an evidence citation and executable check for each rule. Do not invent generic rules unsupported by X1-X3.

X4 must start from the proven v9/v10 hierarchical accumulator architecture, not the current wide per-cycle accumulator and not an unchanged RTL with a tighter clock. Read and reuse the actual implementation evidence in `rtl/int4_mac_v9.v`, `rtl/compute_core_v9.v`, `rtl/mac_array_v9.v`, the corresponding v10 files, and `tb/tb_v9_v10.v` before implementing X4-Y1.

The required arithmetic structure is a signed 12-bit partial/chunk accumulator on the per-cycle multiply-add path plus a signed 24-bit wide accumulator. Fold the 12-bit chunk into the 24-bit accumulator every 16 valid products and flush the final partial chunk before `done`. The 24-bit fold must occur on a separate register-to-register cycle with no multiplier in front of it. Preserve single-add semantics so each registered SRAM result is accumulated exactly once. This is the architectural optimization that previously achieved about 752 MHz versus the roughly 250 MHz wide-accumulator baseline.

The width proof is part of the design contract. For signed INT4, maximum absolute product is 64. Sixteen products require at most 1024 magnitude, which is safe in signed 12 bits. At the 16-bit interface maximum `k_dim=65535`, the worst positive sum is 4,194,240, which fits in signed 24 bits. Do not claim full-range support from width reasoning alone: add latency-aware functional checks across fold boundaries and an adversarial `K=65535` regression, including tail flush behavior, signed extrema, reset/restart, and exactly-once accumulation. Keep the existing K=7, K=0, and K=13 locked regressions too.

X4-Y1's target is 752 MHz, approximately a 1.33 ns clock period, using this hierarchical-fold architecture as the baseline. Y2 through Y5 must push monotonically above 752 MHz. Do not preselect arbitrary targets unsupported by data; after each final extracted report, choose and record the next higher target from achieved headroom and the exact failing path. Every later Y must make an evidence-driven RTL or physical-design improvement before raising the target. The previous 500/600/700/800/900 MHz ladder is superseded for X4 because it would waste iterations below the proven architectural baseline.
